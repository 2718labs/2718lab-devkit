# 交付前验证清单

本文件配合 `SKILL.md` 第 4 步使用。按任务类型对号入座,逐条打勾;不能打勾的项不许说"完成"。可组合内置 `verification-before-completion`、`verify` 两个 skill 一起用(它们提供通用的验证流程,本文件是 2718lab 场景下的具体清单,不重复其内容)。

## 代码改动

- [ ] 改动涉及的每个函数/分支都被实际调用到过一次(不是只静态读代码确认逻辑"应该对")
- [ ] 跑了受影响的旧测试,全部通过(不是只跑新写的测试)
- [ ] 跑了一遍受影响的真实调用路径(脚本/CLI/接口请求),观察到预期输出
- [ ] 检查了改动是否影响了没在计划内、但共享同一文件/模块的其他功能
- [ ] 类型检查/lint 通过(如项目配置了)——但这只是最低门槛,不能替代上面几条
- [ ] 证据在对话中吗?(命令+真实输出是否已经贴出来)

## 新功能

- [ ] 端到端跑通一次完整流程(从触发到看到最终结果),不是只测试内部函数
- [ ] 至少验证一个正常输入 + 一个边界/异常输入
- [ ] 新功能依赖的外部资源(配置项、环境变量、第三方服务)缺失时的报错是否可读
- [ ] 如果有 UI/CLI 输出,实际看过一次真实输出(截图/贴文本),不是只看代码猜测会显示什么
- [ ] 证据在对话中吗?

## Bug 修复

- [ ] 先用能复现问题的最小步骤,实际复现了旧的错误行为(贴出复现时的真实报错/错误输出)
- [ ] 定位到的根因能解释复现现象的每一个细节,不是"看起来像这里"就下手改
- [ ] 应用修复后,同样的步骤跑一遍,证明行为已变为预期(贴出修复后的真实输出)
- [ ] 检查修复是否引入回归——跑一遍该函数/模块原本正常的其他路径
- [ ] 补一个能覆盖这次 bug 的回归测试(没有测试框架时至少留一个可重复的复现脚本)
- [ ] 证据在对话中吗?

## 重构

- [ ] 重构前对现有行为(尤其是边界/异常路径)先跑一遍,留一份"重构前基线输出"
- [ ] 重构后对同一组输入跑一遍,输出/行为与基线一致(不是只凭代码结构"看起来等价")
- [ ] 全量相关测试通过
- [ ] 没有偷偷改变公开接口的行为(参数、返回值、异常类型),如果改了要明确告知用户
- [ ] 性能敏感路径没有引入明显退化(有基准测试的跑一遍基准)
- [ ] 证据在对话中吗?

## 配置与文档

- [ ] 配置文件语法校验通过(JSON/YAML/TOML 等用对应工具真的 parse 一遍,不是肉眼看)
- [ ] 文档里提到的每个文件路径/命令/链接都存在或可执行,逐条验证过
- [ ] 文档里的代码示例实际跑过一次,不是凭印象写的伪代码
- [ ] 改动是否让文档与代码出现新的不一致(例如改了参数名但文档没同步)
- [ ] 多代理工作包已运行 `validate_work_package.py`,产品 brief / index / task cards 没有重新合并成巨型文档
- [ ] 证据在对话中吗?

## 发布类

发布流程细节(版本号、changelog、tag、CI、市场审核)不在本 skill 范围,过程关卡指向 `oss-repo-ops`。本清单只保证发布前验证完成；只有命中危险门禁且用户授权时,才要求额外审查结论没有未回应的致命质疑。

## 常见自欺模式(出现下列短语/行为即违规,停下重做)

| 自欺模式 | 为什么不算数 |
|---|---|
| "跑了 lint/类型检查,应该没问题" | lint 不验证运行时行为,只是最低门槛 |
| "只跑了新写的测试,旧测试没跑" | 旧路径可能被新改动悄悄破坏 |
| "代码逻辑上是对的" | 没有实际执行的"逻辑正确"只是没读出错误,不是验证 |
| "应该没问题" "理论上可以" | 任何以"应该/理论上"收尾的结论都不算验证结论 |
| 复制粘贴上次验证的输出当作本次证据 | 证据必须是本次会话真实产生的 |
| 只演示了正常输入,没碰边界/异常输入 | 边界情况往往才是 bug 藏身处 |
| 验证结果只写在心里/摘要里,没有把命令和输出贴出来 | 没贴出来 = 没有可核验的证据 |
