# DevKit 1.1.1 Local Index and Atlas Maintenance Design

## Status

Approved for implementation on 2026-08-25.

## Problem

The project index is derived state but currently retains every snapshot in one
append-only SQLite database. It grows without a bounded release policy. Atlas,
which is the durable reusable-knowledge plane, has substantial storage and
matching machinery but is not reliably populated and exercised by the normal
local runtime, so users observe an empty or unavailable knowledge base.

## Release boundary

Version 1.1.1 is a corrective release. It shall:

1. make local project-index retention explicit, conservative, and observable;
2. make bundled and accepted local Atlas recipes available through the normal
   runtime lifecycle; and
3. preserve a future boundary for a server-authoritative Atlas without adding
   networking, synchronization, remote leases, or a server in this release.

The project index remains local-only. It is never a remote synchronization
payload.

## Authority split

### Project index

The project index is disposable, reproducible state derived from a registered
workspace. A retained snapshot is not memory. The index may release an old
snapshot only when it is outside every protected root:

- the latest active snapshot for each workspace;
- the immediately preceding snapshot retained for rollback;
- a snapshot referenced by an active task, checkpoint, query receipt, or
  prepared handoff whose retention has not expired; and
- a snapshot explicitly pinned by policy.

Release is fail-closed. An unreadable reference table, unknown schema, active
lease ambiguity, or database error yields a zero-action report.

### Atlas

Atlas is durable reusable knowledge. Accepted recipes, evidence receipts,
templates, and content-addressed payloads are not governed by index retention.
Deleting an index snapshot must not delete Atlas content.

Bundled recipes are immutable distribution assets. Locally accepted recipes
are durable project-scoped Atlas records. Runtime selection joins both sources
through the existing strict matching rules.

## Index maintenance contract

Maintenance has two explicit phases:

1. `preview`: compute a deterministic candidate set and return its identity,
   reasons, estimated row count, and estimated reclaimable bytes without
   mutation;
2. `apply`: re-evaluate all protection roots in one immediate transaction,
   require the preview identity to match, delete only still-eligible snapshots,
   and return actual deletion counts.

Defaults are conservative:

- keep the newest two snapshots per workspace;
- impose no age-based deletion unless configured;
- impose no automatic vacuum or file rewrite;
- never delete the current active snapshot; and
- never run destructive maintenance during bootstrap or a query.

Version 1.1.1 exposes maintenance as a local two-step command. Preview is
non-mutating. Apply requires the exact preview identity, holds the Orchestrator
writer fence while rechecking cross-database roots, and deletes at most 32
candidates. No background or post-sync deletion is enabled in this release.
A future scheduler may invoke this command only under an explicit host policy.

SQLite foreign keys perform the row-level cascade. Maintenance must validate
that every snapshot-owned table is covered by the schema before enabling
deletion. Reclaiming SQLite pages is a separate bounded operation; 1.1.1 may
use incremental vacuum only when enabled and supported, never a blocking full
`VACUUM` in the foreground.

## Atlas activation contract

Runtime bootstrap shall initialize the Atlas database and its content-addressed
root, validate bundled recipes, and make them visible to `atlas_query` and
`atlas_prepare` without requiring an undocumented manual seed step.

The local learning acceptance loop is:

1. an unmatched context returns a bounded non-ready result;
2. an already-authorized acceptance projects one validated recipe bundle into
   Atlas atomically;
3. reopening the runtime preserves that recipe; and
4. an equivalent later context selects it as ready under the existing matcher.

This does not authorize automatic learning from arbitrary model output. Recipe
creation still requires the existing acceptance evidence and validation gates.

## Future server-authoritative Atlas seam

The durable Atlas model shall avoid embedding machine-local absolute paths in
recipe identity. Content hashes, canonical manifests, monotonic revisions, and
compare-and-swap publication are the future synchronization boundary.

A later release may add a server-authoritative provider implementing the same
repository-facing operations. Local 1.1.1 code must not pretend that remote
authority exists and must not add a disabled network client merely for shape.

## Safety and compatibility

- Existing MCP tool parameters and result contracts remain compatible.
- Existing databases migrate forward transactionally and reopen successfully.
- Maintenance touches only the configured project-index database.
- Workspace files, worktrees, checkpoints, Atlas data, receipts needed for
  acceptance, and user-created files are never cleanup targets.
- All tests and temporary roots for this work reside on G:.

## Acceptance

The release is accepted only with current evidence for:

- RED then GREEN tests for preview/apply retention and fail-closed references;
- RED then GREEN runtime test for bundled Atlas visibility and accepted-recipe
  persistence across reopen;
- migration/reopen tests from the previous index and Atlas schemas;
- affected regression, Ruff, Pyright, artifact, and release checks;
- an external build artifact under the G-drive task root; and
- a final dirty-tree review that preserves unrelated work.
