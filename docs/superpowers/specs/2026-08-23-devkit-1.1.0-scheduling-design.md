# DevKit 1.1.0 并行调度设计

## Goal

将 2718lab DevKit 定版为 1.1.0：支持多个互不冲突的写入任务在独立分支/worktree 中并行执行，主协调器在独立审查通过后按证据顺序集成；Fast Lane 同时运行 A2 设计与 Luna A3 预热；宿主已证明的新建/空项目可先走受限索引 bootstrap；候选在显式保留轮次无 rollback 后才可请求宿主清理分支/worktree；并彻底移除无法可靠采集的额度子系统。

## Scope

- Fast Lane 的调度、路由、work-package 和 Relay 合同。
- 多写者 PR-style 候选、审查、rebase/integration proof 流程。
- 有界写入冲突拆分与不可拆分结论。
- 已 attested 的新建/空项目在缺少索引时的受限 bootstrap 路径。
- `gpt-5.6-luna` 独立 A3 预热会话。
- 仅本机 G 盘任务根、缓存和测试临时目录。
- 合并后按显式轮次保留、无 rollback 才可清理的候选分支/worktree 生命周期。
- 插件、Python 包、锁文件、文档和测试同步为 `1.1.0`。

## Non-goals

- 不修改 Codex 宿主的实际模型权限或并发上限。
- 不创建远程 PR、tag、Release、插件安装或网络发布。
- 不把候选提交或局部测试当作主线接受。
- 不从目录名、文件名或 LLM 猜测可拆分写入范围。
- 不把任意 `INDEX_UNAVAILABLE` 视为新项目，或藉此绕过 workspace、capability、lease、scope、review、integration proof 的门槛。

## Architecture

### 0. Scheduler topology V1

Every schedulable plan carries the exact-key `2718lab-devkit/scheduler-topology-v1`
object. Its `plan_binding`, `lease_identity`, and `worktree_identity` are
auditable opaque identity values, not paths, accounts, or chat text. A/B/C are
the main conversation, scheduler, and writer groups. A alone reviews, merges,
and accepts; each B serves at most a `1:3` set of C writers. Each writer needs
a plan-bound lease and independent G-drive worktree. `design` and `prewarm`
are read-only evidence roles, do not count as writers, and remain constrained
by actual host slots, host capability, lease, and safety gates.

Cross-scope work may use only a task-card- or A2-evidence-declared
`declared-child` split. Every split must strictly reduce the normalized
conflict graph. Missing declaration, overlap, unchanged conflict, or invalid
plan/lease/worktree binding is `UNSPLITTABLE_SCOPE_CONFLICT`; never infer a
child or widen scope. This V1 does not restore account-usage quota.
It does not restore D-drive temporary roots.
It does not restore a parent model ceiling.
It does not weaken host capability, lease, scope, review, or safety gates.

### 1. A1/A2/A3 流水线

每个实现单元都有一个权限类型与一个调度阶段：A1 是 `implementation` 写入任务；A2 是独立只读 `design` 任务；A3 是独立只读 `prewarm` 任务。A1 在任务专属的 G 盘 worktree 中取得 lease 后可以写入，A2 和 A3 同时消费绑定同一输入快照的只读上下文。

A2 的设计证据和 A3 的预热证据均绑定 `task_id`、stage、输入 snapshot、context hash 与 artifact hash。二者没有写入范围，不能改变 A1 的 lease、scope、候选提交或接受状态。输入 snapshot 改变会使旧预热/设计证据失效。A3 固定请求 `gpt-5.6-luna` 的宿主已证明可用组合；缺失时产生明确的 `PREWARM_LUNA_UNAVAILABLE`，不静默改用其他模型，也不伪造预热完成。

### 2. 多写者与有界拆分

多个 A1 只有在规范化后的 write-scope 冲突图中互不相邻、依赖已满足、独立 worktree/lease/route 都有效时才能并行。父/子路径、相同文件和 tree/file 交叉均视为冲突。

发生冲突时，调度器只可消费任务卡或 A2 设计证据中显式声明的、互斥的 child scopes。每轮按稳定顺序派生 child task id，并重新验证 schema、依赖图、scope 图、任务数和深度上限。成功拆分必须严格减少冲突；达到上限、没有声明的 child scopes、child 仍冲突或任何验证失败时，返回稳定的 `UNSPLITTABLE_SCOPE_CONFLICT`。该任务由一个写者串行处理，不进行无界重试。

### 3. 审查和主线集成

A1 只能提交本卡 scope 内的候选提交和证据。候选先进入 `review_integration`，独立 reviewer 产出绑定 candidate/base/diff/scope 的 review digest；主协调器再按 integration head 与 proof 的版本顺序 rebase/integrate。第二个候选使用过时 head、错误 scope 或无效 proof 必须失败关闭。只有主协调器可以接受和归档。

### 4. 合并后保留与可验证清理

每个候选可携带显式 `cleanup_policy`，它精确包含有界正整数 `retention_rounds`、真值 `delete_merged_branch`、真值 `remove_disposable_worktree`、绑定候选 branch/head 的 `branch_identity` 与宿主已 attested 可丢弃 worktree 的 `worktree_identity`；未携带该策略的候选永不自动清理。主协调器每完成一个有接受证据的后续集成轮次，才可使已集成候选的 retention round 前进。候选从其 integration proof 生效后连续完成 X 个轮次且没有任何 rollback receipt，才可获得 `CLEANUP_ELIGIBLE` 结论。

`CLEANUP_ELIGIBLE` 不是删除动作。宿主在真正删除前必须重新证明：candidate commit 已包含在当前 integration head、该分支不是受保护/当前分支、没有活跃 lease 或未完成审查、对应 worktree 是 G 盘批准任务根内的可丢弃路径、且没有 rollback。通过后宿主才可删除候选分支及对应可丢弃 worktree；证据、集成 proof、主线和共享缓存不得因该清理删除。任一条件不满足或宿主删除失败都保留全部状态并返回稳定失败码。

### 5. 新项目索引 bootstrap

`INDEX_UNAVAILABLE` 不再单独构成从零项目的调度阻断。只有宿主提供当前、绑定 workspace/repository/input snapshot 的 `new_project_bootstrap_attestation`，并明确证明该项目是新建/空项目且 bootstrap root、初始清单和权限边界有效时，调度器才可生成一个受限的 `bootstrap_index` 初始化操作。它不是普通实现任务的索引豁免：该操作只能建立最小索引/checkpoint 和绑定描述符，不能猜测 write scope、引入未 attested capability、取得 implementation lease 或绕开审查。

Bootstrap 完成后须回传绑定同一 workspace、snapshot、初始清单和生成索引 identity 的 receipt，调度器才可把后续任务放回普通 capacity/lease/scope 图。bootstrap attestation 缺失、过期、identity 不匹配、非空/既有项目、初始化失败或任意其他 index 故障，必须保持 fail-closed 并返回稳定的非成功结论；不得把这些情况伪装为新项目或已启动写者。

### 6. 无额度调度与独立模型选择

1.1.0 完整移除 quota provider、quota balance、quota policy assets、quota schema 字段、quota admission tests 和文档。调度不读取、不缓存、不验证、也不依据账号额度做任何 start/queue/refill 决策。

Fast Lane 路由保留任务风险的不可降级 safety floor、宿主 capability attestation、lease、容量和 write-scope 检查，但不再把子代理限制为不高于协调器模型。宿主为每个 assignment 提供一个精确、已 attested 的 child model/effort/rank；路由器验证其不低于 floor 后原样写入 dispatch receipt，且 `inherit_current_session_model=false`。实际 Codex 宿主若拒绝该 model 组合，必须显式报 `HOST_MODEL_POLICY_DENIED` 或 capability unavailable，DevKit 不得声称已派发。

### 7. G 盘任务根

本机 Fast Lane 根为 `G:\\2718lab\\_codex\\.codex-task-temp`。每个项目任务根下隔离 worktree、`TEMP`、`TMP`、`TMPDIR`、`PYTHONPYCACHEPREFIX` 和 `UV_CACHE_DIR`。路径必须是现存的本地绝对 G 盘非卷根目录，且不得穿过 reparse point。GitHub-hosted CI 继续使用 `RUNNER_TEMP`，不伪装为本机 G 盘。

## Compatibility and migration

- 旧的 quota-bearing Fast Lane 描述符不进入 1.1.0 调度路径；必须明确拒绝或由调用方升级为无额度 schema，绝不部分忽略字段后继续执行。
- 保留 workflow、lease、scope、candidate、review 和 integration proof 的 fail-closed 边界。
- 旧的 `prewarm` 只读语义保持；新增 A2 `design` stage 与 pipeline/split verdict 字段需要 exact-key 验证和稳定 canonical hash。
- 清理策略必须精确绑定 candidate、integration version、branch identity、worktree identity 和 retention round；旧描述符没有清理策略时保持保留，而不是被隐式删除。
- 新项目 bootstrap attestation 是新增精确 schema；没有该 attestation 的旧调用继续保留原有 `INDEX_UNAVAILABLE` fail-closed 行为，不发生隐式降级。

## Acceptance

- 三个互斥 A1 可按可用容量同时调度，A2 与 Luna A3 可和 A1 同时出现。
- 冲突写入任务按显式 child scopes 拆分至无冲突，或得到有限且可重现的不可拆分结论。
- reviewer 未通过、integration head 过期、scope 不匹配或 proof 无效时，不发生 integration。
- 任意额度相关输入不存在于 1.1.0 可执行调度接口；缺失/过期/满额不再阻止合法的 capacity/lease/scope 调度。
- 子模型可与协调器不同，只要宿主已 attested 且满足 safety floor；宿主拒绝必须真实反映。
- 所有本机临时路径验证为 G 盘；版本身份和 release checks 一致为 `1.1.0`。
- 只有连续 X 个已验证轮次无 rollback 的已集成候选才可清理；每个未满足条件、受保护分支、活跃 lease、非 G 盘 worktree 或宿主删除失败都必须保留原分支/worktree。
- 当前且绑定的从零项目 attestation 会生成受限 index bootstrap，而不会因无索引直接得出 `NO_SAFE_WORK`；任意非新项目、过期或伪造 attestation 仍被拒绝。
